Why Correlation-Based Design

// agents grouped by shared data dependency, not org chart

naive-approaches.log

Why the Naive Approaches Fail

  • ✗Single agent — loads every tool description, overflows its context window
  • ✗Monolith — hits the MCP 40-tool ceiling fast
  • ✗Role-based multi-agent — mimics the org chart; tools span roles, so boundaries duplicate and fragment
  • ✗79% context lost per handoff when boundaries overlap
correlation-design.log

What Correlation Gets You

  • ✓90%+ context retained across every handoff
  • ✓Zero tool duplication — each MCP tool belongs to exactly one agent
  • ✓Clean context boundaries — no overlapping toolsets
  • ✓Shared topology backbone — every specialist reads the same world model
method.md

$ correlation = shared data dependency — tools that read/write the same data domain belong together, regardless of job title
$ method — identify correlated tool clusters, draw a boundary around each, assign one agent per boundary
$ result — no agent ever loads a tool outside its boundary, and no tool appears twice

relay-flow.log
1
User posts in a Slack channel
mention the bot — no new channel, no context switching
2
Echobot creates a team task · ~5s poll
persistent poller, not cron — cron's minimum granularity is a minute
3
Relay worker acquires the task
shared queue for the team; graceful shutdown with a grace period
4
Agent session runs in operator mode
~5s for simple questions; longer for investigative work with subagent delegation
5
Response streams back into the same thread
review-first, approve-later — the agent does the first pass, humans stay the approval gate
